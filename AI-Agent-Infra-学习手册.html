从哪一周开始

如果你能独立写 Python CLI、处理 JSON 和 SQLite，并能测试异步超时，可从第 3 周开始。刚接触编程时，先用两到四周练函数、集合、文件读写、异常和调试，再进入第 1 周。

每周怎么学

以每周 8 至 10 小时为参考。用约 2 小时读资料，4 至 5 小时实现，余下时间测故障并整理证据。进度勾选保存在当前浏览器中。时间紧时，先完成各阶段验收，再做选做对比和框架迁移。

每周任务

从原型到可发布版本

01

入门

后端与模型接口基础

岗位对应 模型适配、跨团队协作

用固定模型响应把业务逻辑测清楚，再接真实模型检验输出差异。模拟网络耗时可以测试超时和取消，模型桩无法代表实际模型效果。

第 01 周

把任务做成可测试的程序

学习
熟悉 Python 类型提示、异常、依赖注入、JSON 与 SQLite。把输入校验放在入口，业务函数接收已校验的对象。
动手
先写命令行程序，读取合成工单 JSONL，按 ID 查找工单并返回结构化状态。为正常、缺字段和查无结果各写测试，再把 JSONL 查询换成 SQLite 参数化查询。
验收
命令行返回可解析 JSON。缺字段与查无记录各有稳定的错误码。换存储后通过同一组测试。
第 02 周

给模型调用加超时和并发边界

学习
理解消息、token、结构化输出、流式增量、HTTP 错误以及 asyncio 的取消传播。区分单次请求超时和整个任务的 deadline。
动手
定义 ModelAdapter 和 FakeModel。用 asyncio 同时运行三条模拟请求，并限制最多两个在途调用。让慢请求超时并写下清理过程。后续可换一个真实模型适配器。
验收
记录调用耗时、结果类别和请求 ID。慢请求返回 timeout，结束时无遗留的模拟任务。模型桩无需密钥即可运行。
阶段交付CLI、合成工单夹具、FakeModel、基础测试
复盘题

单次请求剩余 3 秒、整个 Run 剩余 1 秒时，你会给模型多长超时？如果下游已经开始执行，调用方取消意味着什么？

对应阅读 Python asyncio / Python sqlite3 / MDN Server-Sent Events

02

内核

Agent Harness 与执行模式

岗位对应 Harness Kernel、执行架构研发

Harness 决定一轮要调用什么、怎样处理返回值以及何时结束。模型选择动作时，程序仍负责参数校验、预算和终止。

第 03 周

手写一次模型与工具循环

学习
理解工具声明、结构化参数、模型返回工具请求、执行器返回观察结果以及终止条件。用 JSON Schema 描述入参，再由运行端验证。
动手
让 FakeModel 先请求 get_ticket，再根据返回值生成答复。工具注册为名字、schema、处理函数和版本。处理未知工具、缺字段、重复请求和步数耗尽，稳定返回结束原因。
验收
一个测试检查调用顺序。非法工具参数不会到达处理函数。循环在 max_steps 内停止，并记录停止原因。
第 04 周

用同一组任务比较执行架构

学习
理解 ReAct 式交替步骤、固定 Workflow、Planner–Executor 和 Multi-Agent 的控制权位置。执行记录保存动作、输入输出摘要与耗时。
动手
同一个“先查工单，再查询政策，最后回答”的任务实现固定流程和有界循环两版。选做 Planner–Executor，用可校验的任务列表连接两者。多 Agent 先画交接契约，等有明确分工再实现。
验收
用同一批样例比较完成率、工具调用数、耗时和失败类型。拿出至少一例说明什么时候选固定流程。
阶段交付两个执行策略、一份 Trace JSONL 和对比记录
复盘题

如果查政策一定要发生在返回答复之前，你怎么把这条业务要求放进执行器？

对应阅读 JSON Schema 入门 / ReAct 原论文 / Anthropic 工程文章

03

运行时

Managed Runtime 与长任务

岗位对应 状态持久化、断点恢复、故障迁移、弹性运行

Run 状态和 Worker 生命周期分离。给每次模型调用记录结果，恢复时消费已提交结果。跨系统写入仍需要下游去重、查询确认或人工核对。进程死后重建状态和再次向模型求解是两种不同的操作。

第 05 周

为 Run 建立事件与状态模型

学习
Session 关联多次交互，Turn 是一轮发起的交互，Run 是一次可追踪的执行，Event 记录状态变化。Deployment 绑定发布版本，Workspace 定义任务资源边界。项目采用这些自定义语义。
动手
将 run_id、递增 seq、事件类型和数据落库。先用 reducer 从事件重建 Run，再为长历史增加带 last_seq 的快照。写出排队、执行、等待审批、成功、失败和取消的合法转换。
验收
重启进程后，同一事件历史重建相同状态。快照与尾部事件拼接的结果相同。SSE 客户端断线后按游标补读已提交事件。
第 06 周

在 Worker 被杀后继续任务

学习
学习至少一次投递、租约与过期回收、幂等键、重试分类、取消和并发背压。明确“工具已生效，结果还没记账”的故障窗口。
动手
先用 SQLite 事务协调本地队列和 Run 状态，启动两个 Worker 竞争任务。模拟外部写入时使用独立的合成工具存储，让它用稳定操作键去重。给有界重试加退避，对不可确认的写入返回待核对。
验收
分别在取单后、模拟写入后、结果持久化后停止 Worker。新 Worker 能继续任务，模拟写入只生效一次。旧租约持有者无法覆盖新 Worker 的结果。
阶段交付可恢复 Worker、事件存储、三处故障演练记录
复盘题

业务工具已成功扣减配额，Worker 尚未写入成功事件就宕机。工具没有幂等接口，也无法查询结果，你会把 Run 转成什么状态？

对应阅读 Temporal Workflow Definition / Temporal Retry Policy / MDN Server-Sent Events

04

知识

Context、Memory 与检索增强

岗位对应 Context Engineering、分层记忆、RAG、Grounding、个性化

检索返回候选证据，ContextBuilder 决定放哪些证据进模型上下文，生成端负责引用。用户提供的偏好、系统查到的政策、模型写出的摘要具有不同的来源和生命周期。

第 07 周

建立带出处的检索基线

学习
理解分块、元数据、关键词检索、向量相似度和重排。Grounding 要求答案中的关键断言有可核对的资料支持。
动手
整理 30 至 50 段合成政策，写 20 道带证据 ID 的题。用 SQLite FTS5 或简单词频做关键词基线，再试向量检索。中文语料可先验证分词效果。保存文档版本和证据片段 ID。
验收
报告同一批题的 Recall@5，记录没有可用证据时的回复。至少列出五个失败样例，区分召回失败与生成阶段失真。
第 08 周

为上下文设预算并管理记忆

学习
区分本轮工作状态、会话摘要与持久偏好。对上下文分配历史、证据和输出额度，明确来源、归属、访问范围与删除策略。
动手
写 ContextBuilder，按任务、最近交互、摘要和检索证据填入预算。检索时按租户和文档权限限制候选。加两条明确授权的合成偏好，测试写入、纠正、清除和跨租户访问。
验收
保存每段上下文的来源和 token 统计口径。比较有无摘要和重排的引用命中、token 与延迟。清除偏好后，新 Run 的上下文不再包含它。
阶段交付可引用的知识库答复、ContextBuilder、检索评估表
复盘题

召回命中率提高，答案引用准确率却下降，你会在哪几个阶段取样？

对应阅读 SQLite FTS5 / RAG 原论文 / pgvector 官方仓库

05

安全

工具、MCP 与执行安全

岗位对应 Tool、Skill、MCP Server、Sandbox、Credential、Agent Identity

MCP 统一连接能力的方式，权限由实际执行工具的应用和服务判定。练习只调用预先定义的本地工具。学习沙箱时，先确定允许访问的文件路径、网络范围、资源上限和身份。

第 09 周

接入 MCP 并统一工具目录

学习
掌握 MCP 的 Host、Client、Server。区分可调用的 Tool、可读的 Resource、可复用的 Prompt，以及项目可选的任务指引包 Skill。
动手
为本地合成政策库实现一个 MCP Server，只暴露 search_policy。使用官方 SDK 按同一协议版本接入。把 MCP 工具与进程内工具映射到统一注册表，记录工具来源、版本与输入 schema。
验收
同一条查政策用例能走两种适配器。Server 不可用时返回可诊断的错误。运行记录能定位当时调用的版本。
第 10 周

把审批、授权和隔离落在执行端

学习
区分用户身份、Agent 服务身份、凭证与委托范围。理解最小权限、凭证隔离、沙箱边界和审计。把检索资料、工具返回与用户参数当作外部数据处理。
动手
创建模拟写工单工具。执行前验证租户、资源、身份及权限，将审批绑定操作参数摘要和有效期，实际执行时再校验。用假凭证与本地样例验证拒绝分支。阅读容器资源、挂载与网络隔离的边界。
验收
授权写入成功。未授权、审批过期或参数变更被拒绝。审计只记录操作者、工具版本、决策和运行标识等必要字段，测试输出搜不到假密钥。
阶段交付MCP 只读工具、模拟写工具、权限和审批测试矩阵
复盘题

用户批准写入工单 A。等待审批期间参数变成 B，执行端应该凭什么拒绝？

对应阅读 MCP 架构文档 / MCP 安全实践 / Docker Engine 安全文档

06

平台

Agent Control Plane 与版本治理

岗位对应 Agent Artifact、Owner、版本、策略、发布、成本、Managed / BYO Agent

控制面存期望版本，运行端报告实际使用的版本。回滚改变后续流量，已完成的工具写入要按业务规则另行处理。

第 11 周

给 Agent 建立可版本化的发布物

学习
区分配置定义、不可变版本、环境指针和运行记录。把模型配置、Prompt、工具集合、策略、预算和兼容契约绑定到 ArtifactVersion。
动手
写本地 registry，支持创建草稿和构建版本。记录 owner 和租户。发布时原子更新环境指针，Run 入队时锁定版本。接口只允许拥有对应权限的身份发布。
验收
发布 v2 后新 Run 使用 v2，等待审批的旧 Run 继续引用 v1。可以审计发布人、目标环境和变更摘要。
第 12 周

模拟灰度、回滚和 BYO 接入

学习
控制面管理希望运行的版本与策略，执行面消费具体配置执行任务。BYO 指接入自带执行器或 Agent 的场景，需要约定能力、状态和审计接口。
动手
实现按租户或稳定哈希分配版本，保留回滚指针。给平台管理的 Worker 和一个自带 Worker 桩实现同一生命周期接口。记录运行耗时和 token，用预算配置拒绝超额新请求。
验收
用明确的样本分配规则演示灰度。回滚后新 Run 路由回 v1。两种 Worker 都上传统一状态且能追到 ArtifactVersion。
阶段交付Artifact manifest、版本切换测试和回滚演示
复盘题

有一批任务一小时前用 v1 入队，v2 发布后 v1 出现兼容问题。旧 Run 能直接切换到 v2 吗？说明你支持的恢复路径。

对应阅读 Kubernetes Deployment / Kubernetes 组件

07

质量

可观测、评测与持续演进

岗位对应 Dataset、Judge、Trace、Experiment、Run Version、上线 Gate、Bad Case 回流

规则适合断言权限、结构和精确字段。对答案是否完整、证据是否支持断言，可以用人工或校准后的模型判分。线上抽样先去标识、去重和复核，再将典型问题纳入下一版数据集。

第 13 周

把一次失败定位到具体步骤

学习
Trace 串起一次 Run，Span 描述一次模型、检索或工具调用。指标监控趋势，日志补充事件细节。跨进程时传播关联 ID。
动手
记录 run_id、artifact_version、耗时、token 和错误分类。生成一个工具超时和一个检索漏召回的案例，分别定位到对应 Span。对输出日志做字段裁剪，统计请求期间的耗时 p95 和超时率。
验收
凭一条 run_id 能定位模型、检索和工具耗时。日志中没有假凭证。报告注明样本量、统计窗口和估算成本口径。
第 14 周

生成新旧版本的回归报告

学习
规则判分检查 schema、引用 ID 与权限决策，人工标注核对业务正确性。模型评审采用明确 rubric，并用人工样本校准。固定数据集、评审版本和运行配置便于比较。
动手
从研发样例和合成 bad case 整理 50 条起步样本，标注场景、可接受结果与证据。留出独立验证样本。对基线和候选运行同一数据，报告差异、重复运行波动及否决项。
验收
发布门禁对关键权限回归直接拒绝。评测报告给出分母、失败样本和版本。演示一次候选被挡下，再修复、复跑并放行。
阶段交付Trace 样例、回归命令、报告和 CI 门禁
复盘题

整体分数上升，但拒绝未授权写入的测试回归了一例。除了暂停发布，还应查哪些证据？

对应阅读 OpenTelemetry Traces / OpenAI 评测实践

08

交付

生产验证、系统协作与面试

岗位对应 Anchor Tenant、Reference Architecture、前沿探索与跨团队协同

Anchor Tenant 可以理解为提供真实需求和反馈的试点业务方。这门练习用合成数据模拟该角色。跨团队接口从具体故障入手，例如把模型限流信息传给调度端，让运行时据此决定排队与重试。

第 15 周

用一个业务场景跑完整发布流程

学习
选“客服查工单和政策”作为试点场景，写清任务成功、人工转接、权限与延迟目标。掌握队列积压、推理限流、版本兼容和 CI/CD 的协作边界。
动手
在本地模拟试点租户，从构建版本、评测、门禁、发布到运行和收集 bad case。注入模拟模型限流、Worker 故障和文档版本变化。写排障手册，注明模型、数据、安全与发布分别需要谁提供证据。
验收
用一张图说明决策和反馈经过哪些服务。演示一次限流恢复和一次回滚。记录基线、当前结果、样本规模与复现步骤。
第 16 周

整理作品并完成一项有对照的探索

学习
从 Temporal 持久执行、上下文选择、Multi-Agent 或推理延迟选一个问题。先写实验假设，再选相同任务、预算和失败判定做比较。
动手
收齐架构图、设计决策、任务故障记录、检索与评测报告。录一段 3 至 5 分钟演示，展示正常运行、恢复和门禁。用一页参考架构交代未来接入第二个业务需要哪些接口。
验收
能从干净环境用模型桩复现项目，并解释一项妥协、对应指标与适用边界。面试时能说明推理端的首 token 延迟和 Agent 端的队列等待如何分别测量。
阶段交付作品集 README、演示、参考架构、实验对照报告
复盘题

新业务的工具权限模型不同，哪些模块可直接复用，哪里必须增加业务校验？

对应阅读 Anthropic 工程文章 / Kubernetes 组件 / vLLM Paged Attention

贯穿项目

知识库与工单 Agent

用户输入工单编号和问题。Agent 读取工单，检索合成政策并返回带引用的答复。需要修改工单时，它先生成操作预览，等待审批并记录审计结果。服务重启后可以继续已保存的任务，并保留原发布版本。

本地实现范围

用 Python 3.11 或以上版本、标准库、SQLite 和 FakeModel 起步。一个进程先跑通 CLI，再拆 API 与 Worker。数据用合成文档、工单和账号，写操作只作用于本地模拟存储。第 9 周按需接 MCP，真实模型和集群部署可作为扩展。

接口与主要记录
接口作用验证数据
POST /runs校验身份和输入，锁定版本并入队run_id、tenant_id、artifact_version
GET /runs/{id}/events按游标读取事件，可扩展为 SSEseq、type、timestamp
POST /runs/{id}/approvals审批待执行操作，执行时复核action_id、参数摘要、有效期和审批人
POST /releases校验门禁结果后切换环境版本artifact_version、eval_run_id、操作者

最终演示顺序

  1. 提交工单问题，展示可核对的知识出处和模型、检索、工具的耗时。
  2. 在模拟工具写入后中止 Worker。重启后用 run_id 继续，核对工具只写入一次。演示缺少审批时的拒绝。

起步练习 · 约 30 分钟

用模型桩跑一轮工具调用

把代码以 UTF-8 编码存为 starter.py。模型桩先请求 get_ticket，收到工具结果后再给答复。先跑通这条成功路径，再做第 3 周的异常测试。

starter.py
from collections.abc import Callable

TICKETS = {"T-104": "等待退款审核"}


def fake_model(messages: list[dict]) -> dict:
    last = messages[-1]
    if last["role"] == "user":
        return {"tool": "get_ticket", "args": {"ticket_id": last["content"]}}
    return {"answer": f"工单状态为{last['content']}。"}


def get_ticket(ticket_id: str) -> str:
    if ticket_id not in TICKETS:
        raise LookupError("ticket_not_found")
    return TICKETS[ticket_id]


def run(ticket_id: str, model: Callable, max_steps: int = 3) -> str:
    messages = [{"role": "user", "content": ticket_id}]
    for _ in range(max_steps):
        action = model(messages)
        if isinstance(action.get("answer"), str):
            return action["answer"]
        if action.get("tool") != "get_ticket":
            raise ValueError("unknown_tool")
        args = action.get("args")
        if not isinstance(args, dict) or not isinstance(args.get("ticket_id"), str):
            raise ValueError("invalid_tool_args")
        result = get_ticket(args["ticket_id"])
        messages.append({"role": "tool", "content": result})
    raise RuntimeError("max_steps_exceeded")


if __name__ == "__main__":
    print(run("T-104", fake_model))

执行 python -X utf8 starter.py，预期输出 工单状态为等待退款审核。。把输入改成 T-999，预期得到 ticket_not_found。将 FakeModel 改成每一步都请求同一个工具，确认循环在 3 步后停止。

下一步为结果增加调用 ID，把模型动作和工具结果作为配对消息保存。真实模型适配器需要按对应 API 的消息格式编码，工具入口也要补上完整的 schema 和权限校验。

面试准备

用你的实现回答系统设计题

怎么区分 Harness、Runtime 和 Control Plane？

用一次任务讲解。Harness 负责执行步骤，Runtime 负责调度和持久化，Control Plane 负责定义版本、发布规则与预算。准备画出三者传递的版本、事件和任务状态。

至少一次投递下，如何处理重复工具写入？

用稳定操作 ID 标识逻辑操作，由下游持久化去重并返回已提交结果。展示崩溃窗口、租约接管和旧 Worker 的状态写入限制。说明缺少去重或确认接口时如何对账。

引用准确率下降，如何定位？

逐段看候选召回、权限过滤、重排、预算截断和生成。如果证据入了上下文仍答错，单独检查生成与引用映射。准备一条原始样例和对应 Trace。

候选版本更快，能否发布？

使用同一数据集检查任务正确、引用可靠和权限拒绝。对照样本量、p95、成本和失败分布，再按门禁结果决定灰度。说明回滚影响哪些新任务。

任务长时间等待审批时，如何避免占用 Worker？

把等待状态和操作摘要持久化，释放 Worker。由审批或到期事件将任务重新排队，接手时复核参数、版本、身份和有效期。
